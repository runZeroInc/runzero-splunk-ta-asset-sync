# Validating and Updating runZero Asset Sync

This add-on is built with the [Splunk UCC framework](https://splunk.github.io/addonfactory-ucc-generator/)
(`ucc-gen`).

> Prior to late 2026 this add-on was built with the (now end-of-life) Splunk Add-on Builder (AOB).
> See "Migration history: Add-on Builder → UCC" below for why and how it was migrated.

## Building and releasing a new version

1. Install Splunk Enterprise for local testing:
    * Enterprise Free Trial: https://www.splunk.com/en_us/download/splunk-enterprise.html

2. Install [`uv`](https://docs.astral.sh/uv/) if you don't already have it: `brew install uv`.

3. Bump the version in `ucc/package/app.manifest` (`info.id.version`) if this is a new release.

4. Build and package the add-on:
```sh
./scripts/build.sh
```
   This produces `TA_runzero_asset_sync-<version>.spl` in the repo root. **Always use this
   script** rather than running `ucc-gen build`/`ucc-gen package` manually -- see the
   "case preservation" comment block inside `scripts/build.sh` for why skipping it would silently
   break every existing customer's saved account credentials and settings on upgrade.

5. Install the `.spl` in local Splunk Enterprise ("Manage Apps" → "Install app from file") and
   smoke-test it (see "Testing an upgrade locally" below for what to check, particularly if
   you touched `ucc/globalConfig.json`).

6. Run the local AppInspect checks (see below) and confirm no new `error`/`failure`/
   `future_failure` results before uploading.

7. In Splunkbase, under "My Apps" select "Manage App" and then select "In Splunkbase Classic".
   On the version listing, select "New Version" and upload the `.spl`.
    * https://dev.splunk.com/enterprise/docs/releaseapps/splunkbase/managecontentonsplunkbase

## Running Splunk Cloud vetting (AppInspect) checks locally

Splunkbase's Cloud compatibility notices (e.g. "Action required: ... will lose Splunk Cloud
Platform compatibility") are generated by **Splunk AppInspect**, a static-analysis tool run during
Splunkbase submission/vetting. These are packaging/vetting checks, not runtime errors, so simply
installing the app in a local Splunk Enterprise instance will not surface them. To reproduce
and verify fixes for these checks locally, this repo includes a standalone `appinspect/` project
(managed with [`uv`](https://docs.astral.sh/uv/)) that installs the same `splunk-appinspect` CLI
Splunkbase uses, plus `scripts/check.sh`, which drives the workflow.

1. Run the checks:
```sh
./scripts/check.sh
```
   This builds the `.spl` (via `scripts/build.sh`), runs AppInspect against it in `precert` mode
   (the mode used for Splunk Cloud vetting, which includes the `future_failure` checks that
   predict upcoming compatibility loss) from the `appinspect/` project, and prints a summary of
   any non-passing checks. Full per-check detail (file paths, line numbers, remediation messages)
   is written to `appinspect/report.json`.

2. Re-run after making changes to confirm a check's result flips to `success`. Repeat this
workflow for any future Splunkbase Cloud compatibility notice before uploading a new release.

At the time of writing, a fresh build has one expected, unavoidable `future_failure`:
`check_for_custom_mako_templates`, flagging `appserver/templates/base.html`. This file is
generated by `ucc-gen` itself (bundled in every UCC-based add-on as of 6.5.3) and is fully static,
pre-rendered HTML with no Mako code execution -- the actually-dangerous check
(`check_for_existence_of_python_code_block_in_mako_template`) passes. This is a known, confirmed
false positive of the blanket file-presence check, not something introduced by this add-on.

## Testing an upgrade locally

Because Splunk installs/upgrades an app by untarring the new package **over** the existing
install directory (it never deletes files that are absent from the new package), a naive
`rm -rf` + reinstall does not reproduce what a real customer upgrade looks like. Use this
process any time you change `ucc/globalConfig.json` or touch account/settings/input schema:

1. Do a **clean** install of the previous released version first (uninstall/remove any existing
   app directory: stop Splunk, `rm -rf` the app's directory under `etc/apps/`, clear Splunk Web's
   static cache, restart Splunk).
2. Configure real test state through the Splunk Web UI: a Global Account, proxy settings, a
   non-default logging level, and at least one input.
3. Record the "before" state: `local/*.conf` files under the app's directory, and the relevant
   `passwords.conf` stanza (`grep -A2 TA_runzero_asset_sync ... /passwords.conf`).
4. Install the **new** package with the "Upgrade app" checkbox checked -- do *not* clean-reinstall
   for this step, since that's not what customers experience.
5. Reload the configuration page and confirm: the account/proxy/logging tabs still show the
   previously-saved values (not blank), the password field still resolves (shows the masked
   placeholder, not empty), the input is still listed, and saving without re-entering the
   password succeeds (no `KeyError`/404 in `var/log/splunk/python.log`).
6. If a modular input had already run and produced a checkpoint, confirm it resumes from that
   checkpoint after upgrade rather than re-importing/duplicating historical data.

## Migration history: Add-on Builder → UCC

**Why:** Splunk's Add-on Builder (AOB) reached end-of-life on 2025-11-14 at v4.5.1, which bundles
UCC framework 5.48.0. Splunk Cloud vetting now requires UCC 6.3.0+, and no further AOB release
will fix this -- Splunkbase's automated Cloud compatibility notice flagged
`check_for_ucc_framework_version` (among other issues) as a result. The only fix is migrating the
add-on to be built directly with `ucc-gen` instead of through AOB.

**How it was done:**
1. Used the official (experimental) `ucc-gen import-from-aob` command to convert the AOB app into
   a `ucc-gen` source layout (`globalConfig.json` + `package/`). This is largely automatic, but its
   blanket `rm -rf ./package/default/data` step deletes custom dashboards/nav -- these were
   manually restored from the original app afterward. It also does not reliably regenerate
   `lib/requirements.txt`; review it by hand (in this add-on, `requests` was incorrectly commented
   out despite being used, and several stdlib modules were listed as if they were pip
   dependencies).
2. The custom business logic (`bin/input_module_assets.py` -- runZero API paging, checkpointing,
   TLS/proxy handling) is untouched by the migration; it's carried over byte-for-byte, since
   `ucc-gen` only regenerates the modular input's boilerplate wrapper, not this file.
3. Added `"supportedPythonVersion": ["3.13"]` to `globalConfig.json`'s `meta` object. Without it,
   `ucc-gen` omits `python.required` from the generated `inputs.conf`/`restmap.conf`, which
   trips two AppInspect checks (`check_modular_inputs_python_required`,
   `check_admin_external_restmap_conf_python_required`) that weren't in the original AOB output.
4. **The account/settings conf-name casing bug** (see `scripts/build.sh` for full detail): `ucc-gen`
   unconditionally lowercases the REST handler conf-type name it derives for Configuration-page
   tabs (e.g. `TA_runzero_asset_sync_account` → `ta_runzero_asset_sync_account`). There's a
   documented `"conf"` globalConfig.json key that looks like it should override this, but it's
   only wired through to the entity object, not the endpoint's own conf-name used for file
   generation -- confirmed by reading the `ucc-gen` 6.5.3 source and by empirically rebuilding
   with an explicit override, which had no effect. This isn't cosmetic: `passwords.conf` and
   `.conf` lookups are case-sensitive on Linux (which Splunk Cloud runs on), so shipping the
   lowercased output as-is would silently orphan every existing customer's saved account
   credentials and settings on upgrade to the new package -- **this was reproduced and confirmed
   locally** using the "Testing an upgrade locally" process above. `scripts/build.sh` patches the
   built output back to the original mixed case after every build, with a `grep`-based fail-safe
   that aborts the build if any lowercase reference is missed, so this can never be silently
   skipped. This is intentionally a permanent, recurring step (not a one-time migration) -- see
   the comment block in `scripts/build.sh` for the fuller trade-off discussion between this approach
   and a one-time runtime credential-migration alternative.
5. `appserver/templates/base.html` (the original AOB-era file) contained genuine Mako `<% %>`
   Python code blocks (dynamically computing the app name via `cherrypy.request`) and was
   correctly flagged by `check_for_existence_of_python_code_block_in_mako_template`. `ucc-gen`
   generates its own replacement version of this file that's fully static/pre-rendered (see the
   AppInspect section above for why that one remaining `future_failure` is an accepted false
   positive).
6. `ucc-gen build --python-binary-name` requires a Python with `pip` available; macOS Homebrew
   Python blocks system-wide pip installs (PEP 668). `ucc/`'s own `uv`-managed venv (with `pip`
   added as an explicit dependency) sidesteps this.
7. `ucc-gen build` auto-detects a version via `dunamai`/git-tag if `--ta-version` isn't passed,
   which is nondeterministic when run inside this git repo. `scripts/build.sh` instead reads the
   version explicitly from `ucc/package/app.manifest`.
